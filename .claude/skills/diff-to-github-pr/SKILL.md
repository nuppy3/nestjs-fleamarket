# Issue + Diff → GitHub PR 作成ルール

## 前提(絶対厳守)

- **必ず実際のdiffを取得してからPR本文を作成する**。diffを見ずに、issueの受け入れ条件だけから「実装されたであろう内容」を推測して書かない。
- diff取得は `git diff <base>...<branch>` または `git show <commit>` を使う。取得できない場合は、ブランチ名・コミットハッシュをユーザーに確認する。
- **git pushはHTTPS経由(gh認証)を使う。SSH方式(`git@github.com:...`)は使わない。**
  Claude Codeの実行環境は、ホストのSSHエージェント(`ssh-agent`)にアクセスできないため、
  SSH方式のリモートURLだとパスフレーズ入力待ちで無限に停止し、タイムアウトする。
  リモートURLが `git@github.com:...` になっている場合は、
  `git remote set-url origin https://github.com/<owner>/<repo>.git` でHTTPS方式に変更してから進める。
  認証は `gh auth setup-git` 済みであることを前提とする。

## タイトルの命名規則

- 実装PR: `feat: <概要> (SI-XXX)` または `(SI-XXX-YYY)`(範囲は対象issueに合わせる)
- UTのみのPR: `test: <概要> (SI-XXX)`
- 実装+UT混在: `feat: <概要>、<UTの概要> (SI-XXX-YYY)`

## タイトルのプレフィックスの付け方

feat: 機能の追加
fix: バグ修正のみ
docs: ドキュメント変更のみ
style: コードに影響しないスタイルの修正 (white-space, formatting, missing semi-colons, etc)
refactor: バグ修正や機能追加ではないコード変更
perf: パフォーマンス向上のためのコード修正
test: テスト追加・修正のみ
chore: ビルドツールや補助ツール・ライブラリの変更(例:documentation generation)

## 本文テンプレート

概要
<何を実装/追加したかの要約。1〜3文。>

やったこと

- <変更内容を箇条書き。ファイル単位・機能単位で簡潔に>
- スコープ外の変更が含まれる場合も、隠さず記載する(下記チェックリスト参照)

レビュー観点
<diffを読んで見つけた指摘事項。「特になし」の場合は理由を一言添える>

関連

- Closes #<issue番号>
- Jira: <対象サブタスクのURL、複数ある場合はすべて列挙>
- 親ストーリー: <親ストーリーのURL>
- 依存/対象: <関連する他チケットのURLがあれば>

## diffレビューのチェックリスト

本文の「やったこと」「レビュー観点」を書く前に、diffを以下の観点で確認する。

### 基本観点(すべてのPRで確認する)

1. **仕様との整合性**: issue/Jiraの受け入れ条件が、diffの中でどのファイル・どの変更で満たされているか一つずつ確認する。満たされていない受け入れ条件があれば指摘する。
2. **正確性・バグ**: ロジックの誤り、オフバイワンエラー、境界値の考慮漏れがないか確認する。
3. **エラーハンドリング**: 例外・異常系(null、undefined、想定外の入力)の扱いが適切か確認する。
4. **セキュリティ**: 入力値の検証漏れ、認可チェックの欠落、機密情報(キー・トークン・個人情報)のログ出力や埋め込みがないか確認する。
5. **パフォーマンス**: N+1クエリ、不要なループ、過剰なデータ取得がないか確認する。
6. **可読性・保守性**: 命名の分かりやすさ、関数・クラスの責務が適切に分離されているか確認する。

### プロジェクト固有の観点(過去に見つかったパターン)

7. **一貫性の欠落**: 似た処理が複数箇所にある場合(例: `findMany`と`count`)、一方だけ修正されていないか確認する。
8. **ドキュメント/コメントの整合性**: JSDocやコメントが、実際の実装と食い違っていないか確認する。
9. **エッジケースの扱い(truthy判定)**: `&&`による空文字列・0・nullの扱いなど、意図が読み取りにくい条件分岐があれば指摘する。ユーザーが既に「意図的」と明言した内容は指摘しない。
10. **スコープ外の変更**: issueと無関係なファイル・行が含まれていないか確認する。含まれる場合は「やったこと」に明記し、意図的か確認する一文を添える。
11. **未使用コード/テンプレート的な記述**: 空のテストケースやコメントアウトされたコードがある場合、意図を確認する一文を添える。

## レビュー観点の書き方

- 指摘は「〜を確認してください」「〜か判断をお願いします」という、判断を委ねる言い回しにする。「直してください」と断定しない。
- ユーザーから「意図的」「問題ない」という回答があった項目は、次のPR本文更新時に削除する。削除するだけで、経緯の説明は残さない。
- 指摘すべき点がない場合は「特になし。〜のため問題ありません」のように、確認した上での結論であることを示す。

## 作成フロー

1. リモートURLの方式を確認する(`git remote -v`)。`git@github.com:`形式であればHTTPS(`https://github.com/...`)に変更する。
2. diffを取得し、上記チェックリストで確認する
3. PRのタイトル・本文案を作成する
4. チェックリストで重大な指摘(受け入れ条件の未達成、一貫性の欠落など)が見つかった場合は、その指摘内容を明示した上で、**「この内容のまま作成してよいか、それとも修正が必要か」をユーザーに問いかけ、回答を待つ**。ユーザーからの回答を得るまで、PR作成には進まない。
5. 軽微な指摘のみ、または指摘がない場合も、タイトル・本文案をユーザーに提示し、**明確な承認(「OK」「お願いします」など)を得るまでPR作成には進まない**。
6. ユーザーから承認が得られた場合のみ、`gh pr create` 等を用いてGitHub上にPRを作成する
7. 作成後、PRのURLをユーザーに共有する

※ 重大な指摘・軽微な指摘のいずれの場合も、ユーザーからの明確な返答なしにステップ6(実際の作成)へ進んではならない。
